# Задание 3. Проектирование целевой архитектуры и оценка рисков внедрения

Задание: спроектировать целевую архитектуру на горизонт 3 лет в нотации **C4** (контейнеры + компоненты), составить **карту рисков** трансформации и **план управления** ими.

## Ключевые архитектурные принципы (To‑Be)

1. **Data Mesh** — каждый домен владеет своими данными и публикует их как data product с контрактом, SLA и владельцем (Data Product Owner). Новые направления (фарма, электроника, регионы) подключаются как новые data products без врезки логики в легаси.
2. **Событийная платформа** — интеграция через Apache Kafka и Schema Registry вместо точечных синхронных вызовов и общего DWH. Домены обмениваются событиями, что устраняет bottleneck отчётности и ускоряет time‑to‑market.
3. **Портал самообслуживания (Self‑service BI)** — витрина данных с конструктором отчётов, семантическим слоем и RBAC. Медицинские карты и результаты исследований **исключены** из витрины (остаются в защищённом клиническом контуре).
4. **Privacy by Design** — шифрование, аудит, маскирование PII, изоляция мед/фин‑данных на всех уровнях.
5. **Strangler Fig для легаси** — DWH, PowerBuilder, Camel закрываются антикоррупционным слоем (ACL) и выводятся из эксплуатации к концу 3‑го года; новые источники к ним не подключаются.

## Этапы трансформации (из кейса)

- **Этап 1 (0–6 мес):** пилот в 1–2 доменах, единые принципы событий, DLQ, каталог схем.
- **Этап 2 (6–18 мес):** критические домены, потоковые витрины, ACL для Camel/DWH.
- **Этап 3 (18–36 мес):** отказ от синхронных интеграций, доменная потоковая аналитика, вывод легаси.
